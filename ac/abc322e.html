ABC322E Product Development

問題文はこちら。
最小コストで複数パラメータを最大化することを試みる問題。

問題文の端々からDP(動的計画法)の波動を感じる。
・すべての計画案に対して「実行する」もしくは「実行しない」の2択を考える
・選択の過程を全列挙する必要はなく、コストの最小値のみが分かればよい
・制約数値の\(N \leqq 100, 1 \leqq K, P \leqq 5\)はかなり小さい
あたりからだろうか。
以前にも書いた通り、DPは道中の過程をある程度握りつぶして1つにまとめられるのが利点だ。
本来なら\(2^N\)通りの検討が必要なところを、より制約下において小さなパターン数に圧縮できる。基礎技法みたいな教わり方するけど、改めてすごいことを言っているなあと思う。

さて、今回のDPにおいて保持しておくべき情報と遷移方法について考えてみる。
ナイーブには「各計画案を実行した後、K個のパラメータそれぞれがどんな値か？」を持っておきたい。
ただ、「ある計画案を実行した直後にK個のパラメータがすべてPを超えているもの」については、実はすべて同一視してよい。今回はあくまで全部のパラメータがP以上なら良いわけだから、どれくらい超えているかについては全く問題にならず、その中でコストが最小のものを選べばよい。
すると、DPの各遷移のタイミングで持っておきたい情報は\((P+1)^K\)個だ。遷移の回数も考えると、DPテーブル全体は\(N \cdot (P+1)^K\)個の情報を保持する必要があるが、制約下においては十分小さい。
以下、「K個のパラメータの状態」を単に状態と呼ぶことにする。

遷移の方法については「i個目の計画案を実行する」「実行しない」の2パターンで分ける。
\(i=1,2,3,...,N\)について、\(i\)個目の計画案を実行した後に状態\(s\)に辿り着くための最小コストを\(dp[i][s]\)として定義する。\(i=0\)のときは、1つも計画を実行していないときの各状態について考えるものとする。
すると、遷移することを選択した場合、状態sから計画案iを実行した後の状態をtとすると、
\(dp[i][t] = min(dp[i - 1][s] + C[i], dp[i][t])\)
と更新すればよい。また、遷移しないことを選択した場合は
\(dp[i][s] = min(dp[i - 1][s], dp[i][s])\)
として更新すればよい。
初期値は\(dp[0][(0, 0, ..., 0)] = 0\)で、それ以外は無限大で初期化しておく。
こうすれば、常にその時最小の値が更新され続けるはずだ。
一瞬、コスト順に開発案をソートしておく必要があるように思えたが、この遷移方法なら最小のものが出た時点で更新されるはずだから問題なさそうだ（少なくともACはした）。

実装例は以下の通り。見通しよくしたかったので、状態に番号付けをして相互変換している。

import itertools

# 「数値iに対応する状態のパラメータをdの通り変化させた後の状態」に対応する数値を返す
def moveafternum(i, d):
    st_i = Num_to_State[i]
    movedstate = []
    for j in range(len(d)):
        if d[j] + st_i[j] > P:
            movedstate.append(P)
        else:
            movedstate.append(d[j] + st_i[j])
    return State_to_Num[tuple(movedstate)]

N, K, P = list(map(int,input().split()))
Developments = []
for i in range(N):
    Developments.append(list(map(int,input().split())))
Developments.sort()

# 状態と数値を変換（少なくともAC環境では(0,0, ..., 0)が0に、(P, P, ..., P）が末尾に対応する）
Num_to_State = dict()
State_to_Num = dict()
states = itertools.product([i for i in range(P + 1)], repeat = K)
i = 0
for s in states:
    Num_to_State[i] = s
    State_to_Num[s] = i
    i += 1

# dpテーブル構築
INF = 10 ** 12
dp = [ [ INF for _ in range((P + 1) ** K)] for _ in range(N + 1)]
dp[0][0] = 0

# dp遷移
for i in range(N):
    # 計画案iのコストcと、計画案iで変動するパラメータの表dを取得
    c = Developments[i][0]
    d = Developments[i][1:]
    for j in range((P + 1) ** K):
        # 遷移不能な場所からの遷移はカットする（時間短縮）
        if dp[i][j] == INF:
            continue
        # 移動後の状態を示す数値mを取得
        m = moveafternum(j, d)
        # 計画案iを選ぶ場合
        dp[i + 1][m] = min(dp[i][j] + c, dp[i + 1][m])
        # 計画案iを選ばない場合
        dp[i + 1][j] = min(dp[i][j], dp[i + 1][j])

# 遷移不能なら-1、そうでないならdpテーブルの最末尾を出力
if dp[-1][-1] == INF:
    print(-1)
else:
    print(dp[-1][-1])
itertools.productの中身が取り出される順番って環境によって固定なのだろうか？
少なくとも自環境やAtcoderの提出フォームでは上記のコードで動いたが、調べる余地はありそう。

時間計算量は遷移部分の遷移先決定の部分がネックになり、\(O( N\cdot P^K \cdot K)\)になる。
……公式解説見るまで\(\cdot K\)の部分が抜けてた！ Kの値が小さい今回は大した違いが出ないとはいえ、場合によっては計算量が大きく変わるので怖い。

実際の思考の流れとしては漠然と\((P+1)^K\)この情報を持っておけば良さそうだな～とだけ思っており、最初はP以上になるパラメータがあった場合はDPテーブルからはみ出るので切り捨てるとしていた。しかし、よくよく考えてみると超えたやつは全部同じとみなさないと、ちょうどのやつだけ拾うことになってバグると気が付いた。漠然と行けそうだと思ったタイミングで実装を始めるとこうなりがち。
